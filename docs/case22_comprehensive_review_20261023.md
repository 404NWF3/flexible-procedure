# 案例22综合分析：Simio资料、模型口径与优化结果

审阅日期：2026-10-23
范围：本轮提供的四份材料、项目内统一参数契约与成本代码，以及此前审阅的 c20 优化分支。
目的：区分“模型设计”“已生成模型”“已验证结果”，找出影响正式结论的口径差异，并给出下一步顺序。

## 一、结论先行

1. **新 DOCX 是目前最完整的 Simio 建模规格，但它明确写明尚未在 Simio 中建立、运行 SPFX 工程。**其中图是重绘的流程图，不是软件运行截图，因此不能作为模型已完成或已通过 V&V 的证据。
2. **ZIP 含有一个 Simio 模型原型文件、构建器源码和一次交互运行报表；但它不是 DOCX 所描述的自定义 Station/Storage/Resource 版本。**本次未在 Simio 中实际打开该工程。两者的物理参数大体相同，建模架构不同，不应混作同一个版本。
3. **统一加工参数应暂按项目参数契约、ZIP 构建器和新 DOCX 参数表的一致值。**这三者的 P1 总加工均值为 26 分钟。旧 MD 导读的 P1 工序表有漏项和错值，不能作为参数主表。
4. **ZIP 构建器的成本计数方式很可能是“产量相同、成本不同”的直接来源。**它在加工开始时把整段计划加工/换模时间一次性记入总量；SimPy 和新 DOCX 则以实际消耗时间为准，包含 2400 分钟截点前已完成的部分工作。三者口径不一致。
5. 此前 c20 分支报告的 140,782.90 元是特定仿真口径下的**2400 分钟经营贡献均值**，不是净利润，也不是全局最优证明。该方案有明显 P1/P2 低产甚至近似饥饿的现象，必须在报告中披露并加入公平性/等待时间约束后再推荐。
6. 此刻最优先不是继续跑优化，而是锁定参数、修正成本计数、确认实际 Simio 版本/实体上限，再做确定性 V&V。
7. 一台新增机床的 500,000 元应作为资本投资，按使用年限分摊而不是在一个仿真周期内一次性扣除。10 年直线折旧、残值为 0、52 周/年时示例为约 961.54 元/新增专用机床·周；但 100 元/小时是否含折旧、2400 分钟是否代表一个实际生产周都尚待确认。

### 2.1 旧 MD 导读的具体问题

- 它给出的路线是 P1：M1→M2→M3→M4→M5，但工时表把 M2 写成“6（仅 P3）”，没有列出 P1 在 M2 的 8 分钟；P1 实际经过 M2，因此表格不完整。
- 同一张表中，旧 MD 给 P1 的 M3/M4/M5 均值分别为 8/6/4；当前参数契约、ZIP 构建器及新 DOCX 对应值为 6/4/3。P1 的当前基准应为 5+8+6+4+3=26 分钟。
- 若把旧 MD 中 P3 的 M2=6 错套给 P1，且继续使用旧 MD 的其余 P1 工时，会得到 29 分钟；若 P1 的 M2 按路线及统一契约取 8 分钟，则旧 MD 其余错值会得到 31 分钟。无论哪种解释，都不能复现当前契约的 26 分钟。
- “360.8 对比 339.3±30%”“换模非零”“周期时间数百分钟”等，只能作为数量级/合理性检查；不能证明模型逻辑正确、不能代替匹配输入的配对比较，也不能替代置信区间。
- 单次报表中的 M2 利用率约 99.3%支持“该次运行中 M2 接近饱和”的判断；不能单独证明所有场景、所有重复都由 M2 唯一限制。
- 旧 MD 声称 Student 版实体上限为 2500，但当前课程拿到的可能是学术许可版本。须在实际软件的版本/许可窗口核对；不要把旧 Student 限制当成当前许可的既定事实。

### 2.2 ZIP 原型可以证明什么

构建器源码体现了：批次到达后按实体生成单件、单件抽取类型；5 个 EntryQ 各设容量 50；8 台基准机器分别建模；机器换模状态单独保存；实验配置为 0 预热、2400 分钟、10 次重复。它能证明“有一个按件建模的原型及实验配置”，但配置了 10 次重复不等于已经有可审计的 10 次原始结果。

随 ZIP 的 CSV 中有一组单次 Run 数据：

| 指标 | 数值 | 可以支持的结论 |
|---|---:|---|
| 累计创建 | 2747 | 该次运行产生了大量实体 |
| 完工 | 350 | 该次交互运行完成 350 件 |
| 系统内实体最大值 | 2397 | 该次运行接近旧 MD 声称的 2500 上限，但没有超过 |
| EntryQ1 外部等待最大值 | 1974 | 首工位/下游受限时存在较大外部积压 |
| EntryQ2 外部等待最大值 | 321 | 第二入口也出现积压 |

这些数据是一次 Run 的统计，不应标作 10 次重复均值；SPFX 内部虽包含实验结果文件，本次未从 Simio 导出逐重复数据表。因此，旧 MD 的 10 次均值还需在软件结果中导出并复核。

构建日志出现 11 条删除旧 Facility 对象时的 REMOVE FAIL，之后仍打印 experiment configured 和 DONE，没有显示构建器整体中止。但应在 Simio 中检查对象树和连接，排除残留对象/旧连线；不能只凭 DONE 视为无警告成功。

## 三、当前统一模型口径与版本差异

### 3.1 加工参数核对

项目参数契约、ZIP 构建器和新 DOCX 的产品工时表一致：

| 产品 | 路线 | 各工序均值（分钟） | 总加工均值 |
|---|---|---|---:|
| P1 | M1→M2→M3→M4→M5 | 5、8、6、4、3 | 26 |
| P2 | M1→M3→M4→M5 | 4、7、5、6 | 22 |
| P3 | M2→M3→M5 | 6、5、8 | 19 |
| P4 | M1→M4→M5 | 3、9、4 | 16 |

统一其他关键规则：2400 分钟观察窗、0 预热、EXPO(10) 批间隔、DU(5,20) 批量、拆批后逐件抽取 P1–P4=30%/25%/25%/20%、每工位缓冲 50、异类换模 15 分钟、首次及同类免换模、MTBF=EXPO(6000 分钟)、MTTR=EXPO(240 分钟)、加工标准差为均值的 10%。

**建议参数主表继续以项目内 case22_parameter_contract.md 为准；修订旧 MD 导读的 P1 工时表，不要反过来改动契约或 ZIP 参数去迎合旧 MD。**若任务书原文后续有更新，以老师最新任务书为最终依据，并同步更新契约、SimPy、Simio 和报告。

### 3.2 ZIP 与新 DOCX 的模型结构不一致

| 项目 | ZIP 中的原型 | 新 DOCX 描述的目标设计 |
|---|---|---|
| 生产流程 | Source、容量 50 的 EntryQ Server、机器 Server、Connector、Sink | Outside/Buffer/Work Station、Pending Storage、逐台 Resource、过程 Token 控制 |
| 共享缓冲与准入 | 用容量 50 的 EntryQ 和 Server 队列实现 | 显式计数共享 Buffer，Pending 只保存实体引用，Transfer 成功后释放上游机器 |
| 机器派工 | Connector 权重、机器列表优先顺序等原生对象逻辑 | 先选空闲机器，再从共享缓冲候选中按策略选件 |
| 机床数量 | 基准 8 台 | 9 个机器槽位，其中第 7 槽 M4_2 为扩容实验预留，基准禁用 |
| 状态记录 | 有 LastType、TmpProc、TmpChg、产出值等，但响应较少 | 显式记录逐机状态、WIP/External、队列、输出统计及守恒 |

因此，DOCX 应视作下一版实现规格，ZIP 应视作已有原型；需要明确版本号和迁移关系。不能把 DOCX 中的策略或验收表述成 ZIP 已实现。

新 DOCX 的默认方案主要是 baseline、M4 扩容、同类优先、零换模、无故障；aging 是可选扩展。它没有实现或列出 c20 混合策略。c20 必须作为后续新增策略单独实现、验证和比较。

## 四、成本为什么会与产量不一致

项目内 SimPy 指标代码按每台机器累计的 processing + setup 状态时间计算运行费；新 DOCX 也明确要求在运行结束时把截点前实际已消耗的加工/换模时间计入，包括尚未完工实体已经消耗的部分：

**运行费 =（全机实际加工分钟 + 全机实际换模分钟）÷60 × 100 元/小时**

**简化经营贡献 = 窗口内完工产值 − 运行费**

维修、阻塞、空闲不计入这项运行费；设备购置费单列，不混入 2400 分钟运行费，也不应把整笔 500,000 元购置费一次性扣入一个周期。

### 新增设备折旧与回收期补充

暂按直线法、10 年使用寿命、残值 0 进行说明：`期间折旧 = (购置价 - 残值) / (使用年限 × 每年期间数)`。因此新增一台 500,000 元机床，按 52 周/年分摊为 `500,000/(10×52)=961.54 元/周`；按 50 个生产周/年则为 `1,000 元/生产周`。该数值只有在 2400 分钟模型周期被确认代表一个生产周时，才可直接扣入每轮期间收益。若新增机床由多条生产线共用，折旧应按明确的使用/产能份额分配。

当前代码的 `operating_contribution` 是窗口内完工销售收入减已知运行费，不含折旧、材料、税费等未确认成本。运行费默认按实际加工/换模时间计，也支持机床全时或整线全时口径；若任务书的 100 元/小时已经包含折旧，不应再重复扣折旧。`investment.payback_periods` 是新增投资除以配对经营贡献增量均值，单位为仿真观察期；`investment.status` 标记收益非正或区间方向不确定，不可直接将仿真期称为“周”。只有确认 2400 分钟对应一生产周且收益可持续等假设后，才可换算为现实周数。口径见 [`case22_economic_accounting.md`](case22_economic_accounting.md)。

ZIP 构建器则在 Server 的 AssignmentsBeforeProcessing 中执行：

- 先抽取整段 TmpProc 和 TmpChg；
- 随即把完整 TmpProc 加到 TotalProcMin；
- 同时把完整 TmpChg 加到 TotalSetupMin；
- 然后才开始 Server 的 ProcessingTime。

这会把“计划工作量”当作“已经实际消耗的工作量”。在 2400 分钟截点处，若工序只完成了一部分，甚至刚开始，ZIP 的总分钟可能仍按整段时间记账；SimPy/新 DOCX 按实际经过时间累计。因此，即使完工数完全相同，运行费也会不同。该差异是目前最值得先验证的成本口径问题。

### 成本对账的最小检查表

对同一模型、同一重复编号导出以下项目，不要只比较最终结余：

1. 每台机器的实际加工分钟、实际换模分钟、维修分钟、阻塞分钟、空闲分钟。
2. 抽样后计划的整段加工/换模分钟，与运行到截点前已实际消耗分钟的差额。
3. 换模次数是否只在异类切换时增加，首次免换模；是否将维修后续作重复计费。
4. 时间单位是否统一为分钟，换算货币时是否只除以 60 一次。
5. 2400 分钟时未完工实体的部分工时是否计费，而未消耗的剩余工时是否没有计费。
6. 是否混入 Simio 默认 Resource Usage Cost、服务器利用率费用或额外固定/投资成本。
7. 完工收入是否仅对观察窗内真正完工的单件入账。

建议让每台机器在每个工作 Slice 完成后按实际 Slice 累计成本分钟；若 Simio 内置 Server 的过程钩子无法可靠获得截点前实际消耗时间，则用 DOCX 的显式工作片段流程，或使用经验证的运行结束状态时长统计。不要用“进入加工时预记完整时长”代替实际工时。

- 140,782.90 元是所定义假设、成本口径和 2400 分钟窗口下的仿真经营贡献，不是净利润；它未完整扣除材料、折旧、资本成本、销售/需求限制等。

- 此前审阅发现分支的 loop_contract.json 仍写着 design_only_not_executed / enforcement false，而验证文件又记载执行完成。应统一元数据和报告状态，保证可复现审计。
